<BigPicture>

Robots are expensive to run and the world does not repeat itself, so a lot of robot software is written against **recordings**: drive once, record every sensor, then replay the same data at a desk as often as needed. ROS calls a recording a **bag**. Replaying data raises two questions this lesson answers: what time is it, and which reading goes with which? The answers are **header stamps**, **simulated time** and **synchronisation**.

</BigPicture>

<TryThis>

- **Turn `--clock` off.** A sim-time node has no time at all: its timer never fires. This is the classic "my node does nothing" problem when replaying bags.
- **Set the rate to 2.** The node's clock runs twice as fast as real time, and its timer ticks twice a real second, as in the recording of `--rate 2`.
- **Turn `use_sim_time` off.** The node now ignores the bag's time and shows today's date, which is wrong for anything that compares data stamps with "now".

</TryThis>

## Pairing readings by time

The dew point needs a temperature and a humidity from about the same moment. The two arrive at different rates and at different instants, so neither "the latest of each" nor "equal stamps" works. **message_filters** pairs them by stamp. Its ApproximateTime policy waits for readings on both topics and hands your callback a pair whose stamps are close:

<Listing {...code.pairPrinter} highlight={at(code.pairPrinter, 'using Policy', 'temperature_.subscribe', 'humidity_.subscribe', 'std::make_shared<message_filters::Synchronizer', 'registerCallback')} />

It needs `message_filters` as a dependency, in `package.xml` and in `CMakeLists.txt`:

<Listing {...code.syncCmake} highlight={at(code.syncCmake, 'find_package(message_filters', 'ament_target_dependencies')} />

Replaying the weather bag into it, each humidity reading is paired with the temperature reading closest to it:

<Terminal run={r.pairs} />

<PairingPlayground />

<PlainWords>

A synchroniser is a matchmaker with a short memory. It keeps the last few readings from each sensor in a queue (the `10` in `Policy(10)`), and whenever it can form a pair of readings close in time, it calls you with that pair and forgets older ones. You never see a reading that found no partner.

</PlainWords>

## Lab: a weather station's dew point

Make the bag with `python3 /labs/lesson06/make_weather_bag.py /labs/ws/weather`, then write a C++ node:

| | |
| --- | --- |
| Package, node | `weather_station`, the program and node `dew_point` |
| Subscribes | `/temperature` (`sensor_msgs/msg/Temperature`, °C) and `/humidity` (`sensor_msgs/msg/RelativeHumidity`, a fraction) |
| Pairs | with message_filters' ApproximateTime policy |
| Publishes | `/dew_point` as `sensor_msgs/msg/Temperature`, one per pair, with the temperature reading's header |
| Dew point | Magnus formula: γ = ln(RH) + 17.62·T / (243.12 + T), then T<sub>d</sub> = 243.12·γ / (17.62 − γ) |

Build it, run it in one terminal, play the bag in the other, and watch `/dew_point` with `ros2 topic echo`. Check with `python3 /labs/lesson06/check.py`; it makes its own copy of the bag, plays it, and checks every dew point against the readings in it. A reference solution is in `labs/lesson06/solution`.

<Recap>

- A **bag** records topics to a folder (`metadata.yaml` plus `.mcap` files): `ros2 bag record -o NAME --topics ...` or `-a`, then `ros2 bag info` and `ros2 bag play`.
- Replayed messages look exactly like live ones, so you can develop against recorded data.
- A **header stamp** says when data was measured; `frame_id` says where. Pair and compare data by stamp, not by arrival.
- With `use_sim_time:=true`, a node's clock follows `/clock`. Play bags with `--clock`, or sim-time nodes see time zero and their timers never fire.
- **message_filters** pairs topics by stamp: ExactTime needs equal stamps; ApproximateTime pairs readings close in time.
- A value computed from a reading keeps that reading's header.
- Next: describing the robot itself, its links and joints.

</Recap>
