## The design

<CapstoneGraph />

Each choice comes from an earlier lesson:

- **An action** for "drive to (x, y)": it takes seconds, has progress worth reporting, and must be stoppable (Lesson 11).
- **Commands into `/cmd_vel_in`**, so they pass the speed limiter and the watchdog like any other source (Lesson 13).
- **Position from `/odom`**, which Gazebo's DiffDrive publishes; the goal is in the odom frame (Lessons 8 and 9).
- **Parameters** for everything tunable, in one YAML file (Lesson 12): `max_speed`, `max_turn` and `tolerance`.
- **Simulated time** for go_to, like every node that works with the simulation's data (Lessons 6 and 9).
- **The work on a thread of its own**, with a mutex around the pose it shares with the odometry callback (Lesson 15).
- **A bag** of `/odom` and the commands, to check the run afterwards (Lesson 6).

## The controller

go_to needs a rule from the robot's pose and the goal to a velocity command. A simple one that works: turn towards the goal (`angular.z` proportional to the heading error, at most `max_turn`); drive forwards only when facing it within about 0.3 rad, slowing down as it gets close (at most `max_speed`); and stop when within `tolerance`. Try it here before writing it in C++:

<GoToPlayground recorded={recordedPath} />

<TryThis>

- **Lower max_turn to 0.3.** The rover turns slowly before it can set off: the time to arrive grows, the path does not.
- **Put the goal behind the rover**, at (−1, 0). It turns on the spot first, because it only drives when facing the goal.
- **Put the goal at (4, 1).** The path goes straight through a crate. go_to is a controller, not a planner: it knows nothing of obstacles.

</TryThis>

## Beyond this course

go_to drives straight at its goal; a real robot needs to know where things are and plan around them. **Nav2**, the ROS 2 navigation stack, adds maps, localisation in them, global and local planners, and behaviours for when things go wrong, all behind actions like `NavigateToPose`, in the same shape as go_to. **ros2_control** standardises the layer below, between controllers and motors. Both are built from exactly the parts in this course: nodes, topics, services, actions, parameters, frames and launch files.

## The project

Write two packages, using the given `capstone_interfaces`:

| | |
| --- | --- |
| `go_to` | C++ node `go_to`: action server `/go_to` of type `capstone_interfaces/action/GoTo`; subscribes `odom`, publishes `cmd_vel_in`; parameters `max_speed`, `max_turn`, `tolerance`; feedback while driving; stops the robot on success and on cancel; rejects goals while busy |
| `capstone_bringup` | `launch/capstone.launch.py` with a `gui` argument: includes `rover_stack`'s `stack.launch.py` (with the watchdog of the Lesson 13 lab) and starts go_to on simulated time with `config/capstone.yaml`: `max_speed` 0.5, `max_turn` 1.0, `tolerance` 0.1 |
| A run | a bag of a run in `/labs/ws/capstone_run`, with `/odom` in it |

The workspace needs the whole stack: `rover_description`, `rover_sim`, `speed_limiter_interfaces`, `speed_limiter`, `rover_stack` and `cmd_watchdog` from earlier labs (or their reference solutions), and `capstone_interfaces` from `labs/lesson17/interfaces`. `python3 /labs/lesson17/goal_client.py X Y [CANCEL_AFTER]` sends a goal and reports what happened. Check with `python3 /labs/lesson17/check.py`, which drives your robot to (2, −1), cancels a second goal, and reads your bag. A reference solution is in `labs/lesson17/solution`.

- A robot's software is a graph of small nodes; a new capability is one more node that speaks the interfaces already there.
- go_to: an **action** server, reading **odometry**, sending commands through the **safety layer**, configured by **parameters**, on **simulated time**, with its work on its own thread.
- A **bag** of every run lets you check behaviour afterwards and compare changes on the same data.
