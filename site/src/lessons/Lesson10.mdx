<BigPicture>

Topics are for streams: a sensor publishes whether or not anyone listens, and nobody answers. Sometimes a node needs to *ask*: reset this, switch to that mode, what is the value now? and needs to know whether it worked. That is a **service**: a request from a **client**, handled by the one **server** for that service name, and a response back to that client. This lesson calls services from the terminal, defines one in a `.srv` file, and writes a server and a client in C++.

</BigPicture>

## When a topic is the wrong tool

<TopicVsService />

Use a topic when data flows continuously and many nodes may want it. Use a service when one node asks another to do something quick, or to tell it something, and needs the answer before going on. (For requests that take a long time, with progress along the way, there are actions: Lesson 11.)

<TopicOrServicePlayground />

<TryThis>

- **Start the counter late**, at 3 s, as a topic. A and B have nothing until it starts. As a service, they wait for it instead, then get an answer.
- **Make the server slow**, 2 s per request, and have A and B ask at the same moment. The second waits for the first.
- **Compare the age** of the topic answers with the waits of the service answers: freshness costs waiting.

</TryThis>

## Writing a server

A server is a callback, as a subscription is. It receives the request, fills in the response, and returns; ROS sends the response to whoever asked. The counter offers two: `/reset`, of the standard type `std_srvs/srv/Trigger` (no request fields; a `success` and a `message` back), and `/set_step`, of our own type:

<Listing {...code.counter} highlight={at(code.counter, 'reset_ = create_service<Trigger>(', 'set_step_ = create_service<SetStep>(', 'response->accepted = false;', 'response->accepted = true;')} />

<Terminal run={[r.counter, r['counter-info']]} />

<PlainWords>

`async_send_request` posts the question and hands back a **future**, a box the answer will be put in. The answer is delivered by ROS when the node is spun, so the client spins until the box is full. Inside a node's own callback you must not do that: the callback is already running on the thread that would deliver the answer, so it would wait forever. There, pass a second argument to `async_send_request`, a function that ROS calls with the response when it arrives.

</PlainWords>

## Lab: a speed limiter with two modes

Write a node that sits between whatever sends velocity commands and the robot, and limits how fast the robot may go forward or back:

| | |
| --- | --- |
| Service type | `speed_limiter_interfaces/srv/SetMode`, in a package of that name. Request: `string mode`. Response: `bool success`, `string message`, `float64 max_speed` |
| Package, node | `speed_limiter`, the program and node `speed_limiter` |
| Topics | subscribes `/cmd_vel_in` and publishes `/cmd_vel_out`, both `geometry_msgs/msg/Twist`: the same command with `linear.x` kept between −limit and +limit |
| Service | `/set_mode`: `normal` sets the limit to 1.0 m/s, `careful` to 0.3 m/s; both answer `success` true and the limit now in force. Any other mode answers `success` false, says why, and changes nothing |

Check with `python3 /labs/lesson10/check.py`; it publishes commands, calls `/set_mode` with good and bad modes, and measures what comes out. A reference solution is in `labs/lesson10/solution`. Once it passes, put it between `teleop_twist_keyboard` and the Lesson 9 simulation: `ros2 run teleop_twist_keyboard teleop_twist_keyboard --ros-args -r cmd_vel:=cmd_vel_in` and `ros2 run speed_limiter speed_limiter --ros-args -r cmd_vel_out:=cmd_vel`.

<Recap>

- A **service** is a request and a response: any number of **clients**, one **server** per service name. Use it for quick questions and commands that need an answer; use topics for streams.
- A `.srv` file has the request above `---` and the response below; put it in an interfaces package built with `rosidl_generate_interfaces`.
- `ros2 service list -t`, `type` and `call`, and `ros2 interface show`, from the terminal.
- A server is a callback that fills in the response, and should answer every request, even to refuse it.
- A client waits for its server (`wait_for_service`), sends with `async_send_request`, and gets the answer by spinning, or in a callback when inside a node.
- Next: requests that take a while, with progress and cancelling: actions.

</Recap>
