## A robot is a graph

<RobotGraph />

Three words carry the whole lesson:

- A **node** is one running program with one job: read a camera, find a line, steer.
- A **topic** is a named stream of messages, such as `/image`. Nodes **publish** to it, **subscribe** to it, or both.
- A **message** is one piece of data on a topic. Every topic has a fixed message type: an image, a velocity command, a battery reading.

<PlainWords>

A topic works like a radio channel. Anyone can broadcast on it, anyone can tune in, and the broadcaster does not need to know who is listening. Splitting a robot this way means each piece can be written, tested, restarted or replaced on its own.

</PlainWords>

## How nodes find each other

<Discovery />

There is no central server. A new node announces itself, the others reply with what they publish and subscribe to, and matching ends connect directly. Nodes keep announcing themselves while they run and say so when they stop, which is why nodes can start in any order. (Matching ends must also agree on quality-of-service settings; that is Lesson 14.)

<Bridge title="ROS 1">

ROS 1 had a central program, the master (`roscore`), that every node registered with. ROS 2 has none. Older tutorials, and some course pages, still mention the master; in ROS 2 it does not exist.

</Bridge>

The command-line tools join the graph too. A running `ros2 topic echo` is counted as a subscription, but `ros2 node list` hides it; `-a` shows hidden nodes:

## Domain IDs: one network, separate graphs

Discovery reaches every node on the network that shares a **domain ID**, and every node uses domain 0 unless told otherwise. On one robot that is what you want. In a room of robots, or of students, it means everyone's nodes see everyone else's.

<TwoRobots />

The domain is set with the environment variable `ROS_DOMAIN_ID`. Here a talker runs in the default domain, and a listener is started in domain 1:

<TerminalPair>
  <Terminal title="Terminal 2" run={r['domain1-listener']} />
  <Terminal title="Terminal 3" run={[r['domain0-node-list'], r['domain1-node-list-after'], r['domain1-export']]} />
</TerminalPair>

The listener prints nothing and reports no error: it is waiting on a `/chatter` that, in its domain, nobody publishes. That silence is the usual symptom of a wrong domain ID. Prefixing a command sets the domain for that command; `export` sets it for the rest of the terminal session, and a line in `~/.bashrc` sets it for every new terminal. The ROS documentation recommends a number from 0 to 101: the domain ID decides which network ports ROS uses, and other values can run out of ports or clash with ones the operating system hands out. ETH's course has each student pick their own for exactly this reason.

## Your inspection toolkit

| To find out | Run |
| --- | --- |
| which nodes are running | `ros2 node list` |
| what one node publishes and subscribes to | `ros2 node info /node` |
| which topics exist, with their types | `ros2 topic list -t` |
| how many publishers and subscribers a topic has | `ros2 topic info /topic` (add `--verbose` to name them) |
| what a message type contains | `ros2 interface show package/msg/Type` |
| what is being sent | `ros2 topic echo /topic` (add `--once` for one message) |
| how often | `ros2 topic hz /topic` |
| how a node reacts to a message | `ros2 topic pub --once /topic type "{field: value}"` |

`echo` and `hz` run until you press Ctrl+C. If `hz` starts before it has found the publisher, it first warns that the topic does not appear to be published yet; the rates follow a moment later.

</TerminalPair>

## Quiz

<Quiz questions={lesson02Quiz} />

<Recap>

- A ROS system is a **graph**: **nodes** (programs with one job) exchanging **messages** over named **topics**.
- Any number of nodes can publish or subscribe to a topic, and every subscriber gets every message. Publishers do not need to know who listens.
- A publisher and a subscription connect only if the **topic name and message type both match**. A mismatch fails silently; `ros2 topic list -t` shows two types.
- A type such as `geometry_msgs/msg/Twist` is package, kind, name. `ros2 interface show` prints its fields.
- There is **no central server**: nodes discover each other. ROS 1's master is gone.
- Nodes see each other only within the same **`ROS_DOMAIN_ID`** (0 by default). A wrong domain gives silence, not an error.
- The toolkit: `node list`, `node info`, `topic list -t`, `topic info`, `interface show`, `topic echo`, `topic hz`, `topic pub`.
- Next: where your own nodes will live, and how to build them.

</Recap>
