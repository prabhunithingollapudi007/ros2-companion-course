## One job per node

A node should do one thing that can be described in a sentence: drive the motors, estimate where the robot is, limit its speed. Small nodes are easier to test alone, to replace (Gazebo for real motors, a keyboard for a planner), to restart when they fail, and to reuse on the next robot. The cost is more interfaces, so each one should be chosen with care.

<StackLayers />

Most mobile robots divide their software into layers like these. Commands go down, measurements come up, and each layer depends only on the interfaces of its neighbours. The safety layer is where the speed limiter belongs: below everything that might ask for too much.

## Topic, service, action or parameter?

The choice follows from the shape of the exchange:

- **topic**: data that flows, for whoever wants it, with no answer: sensor readings, state, events.
- **service**: a quick request that needs an answer: do this and tell me if it worked; what is the value now?
- **action**: a request for long work, with progress and the chance to call it off.
- **parameter**: a setting of one node, chosen at start, changed rarely.

<PlainWords>

Gazebo's DiffDrive keeps the last command it got (Lesson 9). On a real robot the same happens with many motor drivers. So if teleop crashes, the network drops, or a planner hangs mid-command, the robot carries on at whatever speed it was last told. Teleop sending a stop when you let go of the key would not cover any of those. The fix belongs in the safety layer, where it holds whatever is giving the commands.

</PlainWords>

## Keeping a stack easy to debug

- **Name topics for what they carry**, and keep generic names in the code (`cmd_vel_in`, `cmd_vel_out`): the launch file wires them up.
- **Make every node's state visible**: publish it, log changes once rather than every cycle, and expose settings as parameters someone can read with `ros2 param dump`.
- **Look at the graph**: `ros2 node list`, `ros2 node info` and `ros2 topic info -v` tell you what is connected to what, which is the first question when something does not move.
- **Record a bag** of the interfaces between layers (Lesson 6): a problem you can replay is a problem you can fix at a desk.

## Lab: a watchdog for the stack

Write a node that stops the robot when commands stop, and add it to the stack:

| | |
| --- | --- |
| Package, node | `cmd_watchdog`, the program and node `cmd_watchdog` |
| Topics | subscribes `cmd_vel_in` and publishes `cmd_vel_out` (`geometry_msgs/msg/Twist`): each command passed on unchanged |
| Parameter | `timeout`, a double, 0.5 by default: after that many seconds without a command, publish an all-zero Twist ten times a second until commands come again |
| Stack | in your copy of `rover_stack`, put it between the speed limiter and the robot: the limiter publishes `/cmd_vel_limited`, the watchdog turns that into `/cmd_vel`. Set `timeout` in `stack.yaml` |

You need the whole stack in `/labs/ws/src`: `rover_description` (Lesson 7), `rover_sim` (Lesson 9), `speed_limiter_interfaces` and `speed_limiter` (Lessons 10 and 12; the reference solutions will do), and `rover_stack` from `labs/lesson13/examples`. Check with `python3 /labs/lesson13/check.py`, which tests the watchdog alone, then drives the whole stack in Gazebo and stops sending commands. A reference solution is in `labs/lesson13/solution`.
