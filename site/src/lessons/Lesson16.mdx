## ROS 1 in brief

<MasterVsDds />

Reading ROS 1 code, look for these:

- **roscore**, the master: started first, in every system.
- **catkin**: the build system, with `catkin_make` or `catkin build`; `devel/setup.bash` to source.
- **The parameter server**, global: `nh.param(...)`, `rosparam`, and the private `~` namespace for a node's own.
- **roscpp and rospy**: `ros::NodeHandle`, `ros::Rate` loops with `ros::spinOnce()`, `ROS_INFO`.
- **roslaunch** XML files with `type=` for the program.
- **TCPROS**: connections were reliable by default, with no QoS to choose.

<PlainWords>

Port in this order, and test after each step: interfaces (messages, services, actions) first, keeping their names; then the build files; then the node code; then the launch files; and only then the meaning: QoS, discovery, executors. A ROS 1 node that "worked" while making a blocking call from a callback may deadlock in ROS 2 (Lesson 15), and a subscriber that silently relied on TCP's reliability may need a QoS profile that says so (Lesson 14). Record a bag from the old system and replay it into the new one (Lesson 6): the same input should give the same output.

</PlainWords>

## Both at once: ros1_bridge

A robot can be ported package by package. **ros1_bridge** runs alongside both, passing topics and services between a ROS 1 master and a ROS 2 graph, so ported and unported nodes can talk during the migration. It needs ROS 1 and ROS 2 installed on one machine, which on recent Ubuntu means building one of them from source or using containers, and it is the last thing to remove when the port is done.

<Bridge title="ETH's course">

ETH's fourth lecture is about migrating from ROS 1: why ROS 2 differs (no master, distributed discovery, QoS, executors), a playbook (strategy, interfaces first, build system, node code, launch, then semantics, then validation with bags), the catkin to ament_cmake mapping, a minimal node port, common gotchas (node-local parameters, time, actionlib to rclcpp_action, nodelets to composition, launch), and ros1_bridge for doing it in stages. Its minimal port keeps the ROS 1 loop, with `rclcpp::WallRate` and `spin_some`; this lesson's ports use a timer instead, the more usual ROS 2 shape.

</Bridge>

<Recap>

- ROS 1 had a **master** (roscore), a **global parameter server**, **catkin**, and reliable **TCPROS**; ROS 2 has none of them.
- Mechanical changes: headers and namespaces, `NodeHandle` to `Node`, `advertise` to `create_publisher`, `ROS_INFO` to `RCLCPP_INFO`, catkin to ament_cmake, `type` to `exec` in XML launch files.
- Changes of meaning: parameters belong to nodes, connections have QoS, callbacks run in executors you choose.
- Port in order: interfaces, build, code, launch, then semantics; validate with bags.
- **ros1_bridge** lets ROS 1 and ROS 2 run together during a staged migration.
- Next: the capstone, using everything at once.

</Recap>
